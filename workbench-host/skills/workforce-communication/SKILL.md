# 负责人派工

使用 `wb_delegate_employee` 给名单里的 employeeId 派工。收件人不继承你的聊天，不能写“按上面要求”“等分析员给你”而不提供输入。只传完成本步必要的数据；长资料给 materialId/完整文件名，已保存分析给 taskId、文件名与版本，关键结论和禁止事项短述。不要把整轮聊天、已加载 skill 正文或同一长材料重复复制进去。

任务包保持这五项，短任务一行一个即可：

- **目标**：本步解决什么决策/交付，不扩展用户目标。
- **输入**：真实资料标识或当前必要正文、上一步结论与出处；注明缺失信息、合成数据和推断。
- **输出**：文件名与必要结构，或明确“只回分析，不存中间文件”。不用所有步骤都写文件。
- **验收**：用户明确条件、事实边界、对应员工交代。字数门槛必须引用用户原话；没有就写“无硬字数要求，以完整、准确为准，不因长度重复保存”，不添加“约1000–1500字”之类自定范围。
- **回报**：完成/阻塞/失败，实际成果名与版本，检查结果，缺口与所需下一步。

派工的 accepted 只表示投递。等待原生完成通知，不轮询员工、不另建 agent、不用 send_message 去催、不自己复制做同一工作。下游依赖上游分析时，拿到并核对实际结果后再派；互不依赖的步骤才并行。无需为了“多人”而机械派满所有员工。

原文已上传就传materialId和少量关键结论，不把几千字转写/分析再次复制进task。回报只留负责人验收与下游需要的事实和缺项，不复述整篇原文或将原文包装成成果。简单事实整理由负责人做，别为“分工”多开一个分析会话。

# 执行员工回报

完成时只报：**完成｜成果名 vN（工具成功后的固定链接）｜验收通过项｜尚未执行的人工步骤**。分析不必存文件时，短述事实、推断、缺项和下一步输入，最终回复本身即回负责人。

阻塞时只报：**阻塞｜停在哪一步｜已取得哪些输入｜缺什么/哪个工具不可用｜负责人需要做什么**。失败同样报实际工具原因；未读到材料正文就不能写“文档已分析”，没有文件保存回执就不能说“文件已生成”。不把工具内部字段、绝对路径或完整原稿再抄给用户。

遇到修订，只改负责人列出的差距；同名保存新版本，旧版不变。不要主动“再优化一版”，同一原因重复失败就回报，不隐瞒失败继续循环。

# 负责人核对与交付

读员工真实成果，核对目标与约束；通过则发布员工指定版本，不另存副本。返工包只给差距、依据和要修的段落，不重发全部任务。交付按短回执说：**已交付文件与版本｜对应用户哪条要求｜缺什么输入、哪些步骤要用户自己做**，不要求固定字数；保存文档与实际外部操作分开说。阻塞不是闭环完成。
